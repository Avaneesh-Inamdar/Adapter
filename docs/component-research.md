# Component feasibility research

Research date: 2026-10-21. Scope: Windows x86-64 host, existing Intel Mach-O binaries. These are observations from upstream documentation and source, followed by explicitly marked engineering inferences. No candidate was built or executed as part of this research; upstream Windows support is not a local verification result. This document does not select the final stack.

## Mach-O parser candidates

All three candidates parse foreign files; none of these observations establishes a Windows Mach-O execution runtime. A parser remains separate from segment mapping, dyld fixups, symbol binding and ABI adapters.

| Candidate | Observed features | Windows integration and dependencies | License | Reuse assessment and unresolved gap |
| --- | --- | --- | --- | --- |
| LIEF | C++/Python/Rust binary inspection/manipulation; Mach-O universal binaries and chained-fixup access appear in upstream examples. | Official installation documentation describes a win64 SDK, DLL/static libraries and Visual Studio integration. Source uses CMake/C++; Python bindings provide another integration route. SDK CRT settings must match the host build. | Apache-2.0 for open-source LIEF. | **Inference:** strongest immediately documented native Windows SDK option; higher-level Objective-C and dyld shared-cache features are listed under LIEF Extended, so verify feature availability before depending on them. Pin a release and probe exact malformed-input behavior. [features/license](https://github.com/lief-project/LIEF/blob/main/README.md), [Windows SDK/CRT](https://lief.re/doc/latest/installation.html). |
| Rust `object` | Unified ELF/Mach-O/PE/COFF/Wasm/XCOFF/archive reading; low-level raw format APIs and unified section/symbol access. Writing supports Mach-O relocatable objects, not a general Mach-O executable linker. | Cross-platform Rust library; no OS loader dependency is implied by reading bytes. A Windows Cargo build and toolchain availability still require local checks. Minimal feature selection can avoid decompression dependencies. | MIT OR Apache-2.0. | **Inference:** good parser foundation when choosing Rust, especially with raw Mach-O access retained. Upstream explicitly assumes trusted inputs, limits denial-of-service mitigation, and does not reproduce platform-loader behavior; add file/count/size/work limits. [capabilities and security limits](https://github.com/gimli-rs/object), [features/dependencies](https://github.com/gimli-rs/object/blob/main/Cargo.toml). |
| Rust `goblin` | Cross-platform, endian-aware Mach-O 32/64 parsing, alongside ELF/PE/archive formats; `no_std`/feature configuration and fuzzing are documented. | Requires a supported Rust toolchain; README currently specifies Rust 1.85 / edition 2024. A native Windows build is plausible from its design, but was not run here. | MIT. | **Inference:** compact alternative with Mach-O-specific structures. Audit exact dyld opcode/chained-fixup/modern-load-command coverage against chosen fixtures rather than assuming complete dyld support. Upstream Mach-O maintainer list invites additional maintainers. [README](https://github.com/m4b/goblin), [license](https://github.com/m4b/goblin/blob/master/LICENSE). |

## Compiler/linker and call-boundary evidence

| Candidate | Established capability | Windows feasibility and remaining gap | License |
| --- | --- | --- | --- |
| Clang + LLD Mach-O | Clang is a cross-compiler selected by target triple. LLD has a Mach-O linker (`ld64.lld`) accepting Apple's ld64-style arguments. | **Inference:** suitable route for deterministic SDK-free Mach-O assembly/C fixtures. Installed Windows distributions must be inspected: presence of `clang.exe` or `lld-link.exe` alone does not prove a Mach-O linker driver is included. Actual compile/link tests remain necessary. Ordinary macOS programs also need target headers/libraries/SDK stubs, not host Windows libraries. | Apache-2.0 with LLVM exceptions. [cross compilation](https://clang.llvm.org/docs/CrossCompilation.html), [Mach-O linker](https://lld.llvm.org/MachO/index.html), [license](https://github.com/llvm/llvm-project/blob/main/llvm/LICENSE.TXT). |
| cctools-port / ld64 | Current README lists x86-64 macOS targets and Linux/BSD/macOS/iOS hosts; dependencies include Clang, C++20 library, libdispatch/BlocksRuntime, and TAPI for SDK stubs. | Current supported-host list does not include Windows. Older release descriptions mention Cygwin; that does not verify current native Windows support. **Inference:** secondary fixture-generation alternative if independently built/tested; not a runtime solution. | Apple-derived cctools contains APSL-2.0 `COPYING`; audit notices for each imported component. [current hosts/dependencies](https://github.com/tpoechtrager/cctools-port), [older releases](https://github.com/tpoechtrager/cctools-port/releases), [license text](https://raw.githubusercontent.com/tpoechtrager/cctools-port/1030.6.3-ld64-956.6/cctools/COPYING). |

Clang documents `__attribute__((sysv_abi))` on Windows x86-64 as selecting the calling convention used by Mac/Linux/BSD. Microsoft documents native Windows integer argument registers RCX/RDX/R8/R9, stack home space, and its own aggregate/variadic rules. **Inference:** narrowly typed bridge functions can be investigated with this attribute; casting a Windows function pointer to a guest function pointer is insufficient. Shared CPU architecture does not remove structure-layout, varargs, exception-unwind, TLS, object-runtime or operating-system differences. [Clang attribute](https://clang.llvm.org/docs/AttributeReference.html#sysv-abi), [Windows calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170).

## Recommended experiments before component selection

1. Build the inspector against one pinned parser on the actual Windows host. Check thin/fat inputs, malformed range handling, load commands, imports, symbols and JSON determinism against generated fixtures and an independent parser.
2. Inspect the local Clang/LLD distribution; compile and link a minimal Intel Mach-O fixture without Apple SDK dependencies. Preserve exact commands and distinguish a cross-built fixture from a genuine macOS-built reference application.
3. Prove scalar guest-to-host and host-to-guest call boundaries with mixed arguments and stack alignment. Add aggregates/varargs only with explicit ABI cases.
4. Keep framework/runtime providers modular. Treat GNUstep and libobjc2 as unintegrated candidates until an actual Apple-ABI metadata consumer proves the necessary adaptation.
5. Prefer a dependency-driven subset over importing every POSIX facility. Record exact Darwin semantics and layout at each adapter boundary; select a larger backend only when it reduces demonstrated work.

Maintenance evidence is limited to live upstream documentation, source and advertised CI; release cadence, outstanding defects, transitive-license completeness and current local compiler compatibility were not audited. All Windows build/run cells remain locally **unverified** until recorded experiments pass. No source code from these projects was copied by this research.
